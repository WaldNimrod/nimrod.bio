### F-003 — Gallery pages overflow horizontally (no `<img>` width constraint) — **S2 — NEW**
- **Pages:** `/project/hagina-shel-nimrod/` (scrollWidth 4294 desktop / 2082 mobile375) and `/project/rest-x-greenhouse/` (4294 / 2082). All other 10 pages == viewport.
- **Root cause (CSS, confirmed by source read):** gallery `<img>` elements carry size classes directly on the img — `<img width="1024" height="684" class="img-ph g-wide">`. The grid in `nimrod.bio/wp-content/themes/nimrod-bio-2026/assets/css/t3.css` (lines 213–226) defines `.gallery { display:grid; grid-template-columns:repeat(4,1fr) }` and `.gallery .g-wide/.g-square/.g-tall` track spans, but the `width:100%`/`object-fit` rule (`.img-ph > img { width:100% }` in t1/t2/t8.css) only targets an img that is a **child** of `.img-ph` — here the img **is** the `.img-ph`. There is **no global `img{max-width:100%}` reset** in the theme. So each gallery img renders at its intrinsic `width="1024"` HTML attribute and blows the grid out to ~4294px.
- **Reproducibility:** caused by the `width="1024"` attribute, so it manifests independent of whether the image bytes paint (not merely a headless lazy-load artifact). team_100's "galleries render real uploads" [D] is true at the data layer; the *layout containment* is the defect.
- **Impact:** visible horizontal scroll / squeezed content column on both gallery project pages, worst on mobile375. Evidence: `project-hagina_desktop.png`, `project-hagina_mobile375.png`, `project-rest-x-greenhouse_*.png`.
- **Suggested fix (team_35):** add `.gallery .img-ph, .gallery img.img-ph { width:100%; height:100%; object-fit:cover; max-width:100% }` (or a global `img{max-width:100%;height:auto}` reset) so gallery imgs fill their grid cell instead of expanding to intrinsic width. **No theme edit performed by team_50.**

### F-004 — Public email `nimrod@nimrod.bio` displayed (contact card + sitewide footer) — **S2 — NEW (policy reconcile)**
- **Where:** (a) `/contact/` "אימייל ישיר" card — `<a href="mailto:nimrod@nimrod.bio" class="direct">nimrod@nimrod.bio</a>` (visible, designed block with copy "אם מעדיף אימייל פרטי"); (b) **site footer** "קשר" column — same `mailto:` link, appears on **every** page (home/about/contact all = 1 hit).
- **Conflict:** mandate task 4 requires "/contact/ displays NO public email address." The rendered design publishes the email deliberately, both on /contact/ and sitewide.
- **Disposition:** NOT auto-classed as a bug — it reads as an intentional design/content choice. Needs team_00/team_35 reconcile: either the no-public-email directive holds (remove both occurrences, rely on the form + WhatsApp) or the directive is relaxed. Flagging because it directly contradicts the stated acceptance criterion. (Note: a published mailto is a spam-harvest exposure if the no-email rule was a privacy/anti-spam decision.)
